真实研究示范不等于正式可发表论文。没有课堂数据时采用真实文献语料分析路线；模拟课堂数据只能放独立标记 SIMULATED 的回归项目，不能进入 E04/E05 的实际研究结论。关键方向选择由真实用户回答或使用用户已明确的选择；不得由开发 agent 冒充用户确认。可预设剧本的自动测试必须与 live 记录分开。

## 八、证据、缺陷与完成定义

每条验收只允许 passed / failed / blocked。必需项不允许用 skipped、未测试、未来支持替代通过。对版本能力确实不适用的细节需写出等价验证方案和理由；不能用此方式豁免核心功能。

证据至少包含：执行 commit、依赖/运行时版本、测试机器、输入文件 hash、实际命令/操作、返回码或实际界面状态、日志/截图/成果相对路径。截图只能证明可见界面，不能证明底层数据正确；两者配套。

所有脚本/自动化用真实结果填报告，禁止根据预期伪造 PASS。关键文件篡改、越界写入、凭据泄漏、静默覆盖、重复执行、虚构证据属于发布阻断问题。修复后运行针对性回归以及受影响链路；无变更不反复跑昂贵 live。

只有同时满足以下条件才能把 Goal 标为完成：

1. WF01–WF12、REL01–REL03、WB01–WB20、E01–E06 全部有通过证据；原方案场景与 PRD AC 全部有映射。
2. 工作流新版本已在 GitHub 实际发布，远端资产下载安装复测通过，本机两处安装一致。
3. 工作台交付真实可运行 Windows 包，真实 Codex/MinerU 集成和完整研究样例达标，工作台源码/发布资产按用户仓库策略上传并核验。
4. 必需自动化测试、类型检查、构建与打包检查成功；没有遗留发布阻断缺陷。
5. 交付文件、版本、路径、仓库/Release 链接、限制和复现步骤完整；真实私密数据不在远端发布包。

## 九、阻塞处理与目标持续性

登录、账户选择、真实研究关键决定等只有用户能提供的信息，可集中询问最少必要问题；等待时继续其他独立且顺序允许的工作。不能把技术难点、长耗时或尚未开发写成外部阻塞。

如果同一外部阻塞反复出现且无法继续，按实际 Goal 工具的阻塞条件更新状态，并留下已完成、剩余验收、恢复条件。不能因时间/预算接近就写 complete，也不能编造 GitHub URL、发布版本、实验结果或测试成功。用户要求暂停时按工具规则暂停并报告；没有暂停指令不自行终止整个目标。

## 十、最终对用户的交付格式

简明说明完成的两个版本，附仓库/Release 和 Windows 包链接；列出真实运行时及样例范围；概括验收通过数量并链接完整矩阵；说明仍属于后续版本的第三方 API 能力。若未全部达标，明确未完成项及原因，不使用“已全部完成”。

执行者的第一步：创建/核对 Goal，读两份 v0.2 与本验收矩阵，建立 GOAL_STATUS，开始 G0 基线核查。
